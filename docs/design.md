## 1. 项目定位与设计哲学

### 1.1 一句话定位

> **机器补记忆，人补导航。** 一个纯本地的只读提醒器，在玩家正常玩金铲铲 PC 版「大橘大利」模式时，把屏幕上出现过的公开信息截屏、识别、记录、推演，在关键时刻提醒玩家不要漏掉关键操作。

### 1.2 它不是什么

| 不是 | 理由 |
|---|---|
| 不是自动化脚本 | 零输入模拟。不代点、不代拖、不代 D 牌。玩家双手全程在键盘鼠标上 |
| 不是外挂 | 零进程读取、零内存读取、零抓包。感知边界永远停留在"截屏像素"级别 |
| 不是云工具 | 零联网外传。所有计算在本机完成，数据不出本地 SQLite |
| 不是 LLM 应用 | LLM 只在开发期当"编译器"（辅助结构化数据），运行时是纯规则引擎 |

### 1.3 四条设计哲学

1. **只读感知**：工具看玩家能看到的，不多看一像素。棋盘、商店、备战席、玩家列表——凡是玩家眼睛能看到的信息，工具截屏识别；凡是需要翻页才能看的（对手棋盘详情），由人按 Tab/E 导航，机器被动记录。
2. **规则先行**：决策知识全部来自攻略 JSON（38 任务逐阶段变体、层数里程碑、达标即停原则），不引入运行时 AI 推理，保证行为可解释、可审计。
3. **数据闭环**：每局识别结果落 SQLite，胜负回流入库，战力评分权重靠历史数据自校准，启发式从"拍脑袋"走向"自校准"。
4. **五五开留给人**：对位引擎停在 L1.75（主C精细+炮灰折算），覆盖 ~90% 场景；真正需要博弈判断的五五局，提示信息但不代决策。

## 2. 系统架构总览

```
┌─────────────────────────────────────────────────────────────┐
│                        交互层（Overlay）                      │
│   HUD 常驻面板（角落小窗） + Toast 提醒（条幅弹窗）              │
└────────────────────────────┬────────────────────────────────┘
                             │ 渲染
┌────────────────────────────┴────────────────────────────────┐
│                        决策层（规则引擎）                       │
│  ① 层数进度模块   ② 战力评分模块   ③ 对位预测模块   ④ 影响推演  │
│  （攻略 JSON 驱动 · 零 LLM · 全部可解释规则）                  │
└────────────────────────────┬────────────────────────────────┘
                             │ 查询
┌────────────────────────────┴────────────────────────────────┐
│                        知识层（数据三腿）                      │
│  数值库（掌盟+公告）  ·  模板库（对局积累）  ·  对局库（SQLite）  │
└────────────────────────────┬────────────────────────────────┘
                             │ 读写
┌────────────────────────────┴────────────────────────────────┐
│                        感知层（截屏识别）                       │
│  mss 截屏 3-5Hz → OpenCV 模板匹配 → PaddleOCR 本地推理          │
│  （只读屏幕像素 · 不碰进程 · 不碰网络）                          │
└────────────────────────────┬────────────────────────────────┘
                             │ 截取
                    【金铲铲 PC 版游戏画面】
```

五层自下而上：**感知 → 知识 → 决策 → 交互**，外加贯穿全程的**数据沉淀**（SQLite）。每层职责单一、可独立替换，这是后续版本迭代不推倒重来的关键。

## 3. 感知层设计

### 3.1 技术栈

| 组件 | 选型 | 职责 |
|---|---|---|
| 截屏 | `mss` | 全屏/区域截图，单帧 ~30ms |
| 定位 | `OpenCV` 模板匹配 | 图标锚点定位（金币框、血条、棋盘格、星级角标） |
| 识别 | `PaddleOCR`（本地推理） | 数字与文字（层数、金币、血量、弈子名） |
| 调度 | Python asyncio 循环 | 3-5Hz 轮询，按场景降频 |

### 3.2 感知清单（识别什么）

| 信息 | 采集方式 | 频率 | 难度 |
|---|---|---|---|
| 当前层数/金币/血量/等级 | 数字框锚点定位 + OCR/数字模板 | 3-5Hz | ★☆☆ |
| 商店 5 张卡 | 卡片模板匹配 | 选牌阶段 5Hz | ★★☆ |
| 备战席/场上弈子 | 头像模板匹配 + 星级角标 | 5Hz | ★★☆ |
| 装备（成装/散件） | 装备图标模板 | 5Hz | ★★☆ |
| 回合公告（下回合对手） | OCR | 出现时 5Hz | ★☆☆ |
| 玩家列表（按E） | OCR + 等级/血量数字模板 | 打开时 5Hz | ★☆☆ |
| 对手棋盘（按Tab轮播） | 头像/装备/羁绊模板 | 巡视时 5Hz | ★★★ |
| 任务进度 | 任务图标锚点 + OCR | 备战 3Hz | ★★☆ |
| 弈子技能倍率 | 不采集 | — | — |

**模板库规模**：60+ 弈子 × 3 星级 ≈ 180 个头像模板 + 30 个 UI 锚点 + 10 个装备图标 ≈ **220 个模板**。全部来自玩家自己截图裁剪，零爬虫零解包。

### 3.3 场景分频轮询

不同游戏阶段信息变化频率不同，按场景调度截屏频率，降 CPU：

| 场景 | 频率 | 识别目标 |
|---|---|---|
| 备战/选秀阶段 | 5Hz | 商店、备战席、层数、金币、血量 |
| 战斗阶段 | 1Hz | 仅血量、层数（战斗中无操作） |
| 玩家列表打开时（按E） | 5Hz | 7 家对手的等级/血量/羁绊概览 |
| 对手棋盘巡视时（按Tab轮播） | 5Hz | 对手弈子、装备、羁绊、层数 |
| 局前/局后界面 | 0.5Hz | 检测对局开始/结束标记 |

### 3.4 感知层三级降级（韧性设计）

截屏 API 被游戏反作弊或系统更新干扰时，工具按以下熔断链降级，保证"永不全灭"：

| 级别 | 触发条件 | 状态 | 用户感知 |
|---|---|---|---|
| L0 正常 | mss + D3D 截屏正常 | 全功能 | 无感 |
| L1 自动切换 | D3D 失配（黑屏/花屏帧占比 >30%） | 切 PIL ImageGrab 兜底 | 识别频率略降 |
| L2 降频保命 | 全帧失配 | 只跑 0.5Hz 数字模板（内存 OCR） | 仅层数/血量/金币提醒 |
| L3 仅局外 | 截屏被完全封锁 | 卡组参谋 + 局后复盘仍可用 | 工具变局外工具 |

**实现**：场景调度器每 100 帧统计黑屏率，超阈值自动降级并 Toast 告知；恢复后自动回升。工程量 +1 天（D27 顺带）。

### 3.5 模板冷启动与自动补全

- **冷启动**：首局前用模拟器+录屏，人工截 50-80 个核心模板（商店五卡、层数框、金币框、主流弈子）
- **自动补全**：运行时遇到未识别棋子（匹配置信度 < 0.7），自动裁剪该区域截图存入 `pending_templates/`，局后人工一键确认入库——**越打越全，冷门弈子打几把就齐了**
- **版本更新**：新版本立绘更换导致旧模板失配，自动落 `pending` 目录走人工确认流
- **ROI 坐标版本化**：UI 布局（金币框/血条/棋盘格锚点坐标）随版本可能改动，坐标配置与模板同目录版本化（`templates/v18.6/anchors.json`），版本切换时整目录隔离，避免新旧坐标串档

（原 3.4 节序号顺延为 3.5，原 3.5 感知精度指标顺延为 3.6）

### 3.6 感知精度指标

| 指标 | 目标 | 验证方法 |
|---|---|---|
| 弈子识别准确率 | ≥95% | 人工标注 200 帧对答案 |
| 数字OCR准确率（层数/金币/血量） | ≥98% | 同上 |
| 场景判断准确率 | ≥95% | 同上 |
| 单帧处理延迟 | ≤150ms | 日志统计 P95 |
| CPU占用（i5级别） | ≤15% | 运行时监控 |

## 4. 知识层：数据三腿

### 4.1 三腿总览

| 数据腿 | 内容 | 来源 | 维护方式 |
|---|---|---|---|
| ① 数值库 | 弈子血攻防/攻速/技能倍率、羁绊断点效果、装备属性 | 掌盟资料库（官方内容，半自动爬 H5） | 首次批量 + 每版本 30min（LLM 辅助结构化） |
| ② 模板库 | 弈子头像、UI 锚点、装备图标（~220个） | 玩家对局截图 | 越打越全，自动积累 |
| ③ 对局库 | 每局快照（阵容/装备/层数/血量/胜负） | 运行时自动落库 | 自动，无需维护 |

### 4.3 数值库数据源详解

**为什么是掌盟**：游戏内图鉴和掌盟资料库是唯二全量官方内容源。游戏内图鉴只能截屏，掌盟是 H5 页面可爬。DataTFT 等攻略站偏云顶，金铲铲特有内容（大橘大利、时间卡片）缺失。

**爬取流程**（半自动，每次 30 分钟）：
1. `requests` 拉取掌盟金铲铲资料库页面（弈子/羁绊/装备三个列表页）
2. `BeautifulSoup` 解析 HTML，输出中间格式
3. LLM 辅助结构化：HTML 片段 → JSON schema（LLM 只在开发期，不进运行时）
4. 人工抽检 10 条 vs 游戏内图鉴，确认无误后入库

**版本追更流程**（每版本 30 分钟）：
1. 读官方版本公告，提取改动清单（弈子增删、数值调整、羁绊重做）
2. 重跑爬取脚本刷新数值库
3. diff 新旧 JSON，人工确认改动点与公告一致
4. 入库并更新 `version` 字段（如 `18.6` → `18.7`）

### 4.4 知识库版本对齐三重校验（防串档）

游戏版本切换日（如 18.6 → 18.7）是数据污染高发窗口。三重校验：

| 校验层 | 机制 | 拦截什么 |
|---|---|---|
| 数值库 | 文件名带版本 `rules_v18.7.json` + 文件头 `meta.version` 字段 | 加载错误版本的数值 |
| 对局库 | 每行 `version` 列；入库时校验与运行时版本一致 | 旧版本对局数据混入新版本统计 |
| 模板库 | 按版本目录 `templates/v18.7/`，ROI 坐标同步版本化 | 旧模板/旧坐标静默失配 |

**版本不匹配 = 拒绝入库 + Toast 警告**，不静默跳过。工程量：D1-3 与数据层同步定义，零额外排期。

### 4.5 数据红线

- 只爬公开 H5 页面，遵守 robots.txt，限频 1req/s
- 上述三重校验为 CI 检查项：semgrep 规则 tft-versioned-knowledge 拦截无版本号的知识文件引用
- 不碰客户端文件（解包 = 腾讯加壳 + 用户协议禁逆向 + 触红线，明确排除）
- 不用任何需要破解的第三方数据源

## 5. 决策层：四大模块

决策层是工具的"大脑"，全部规则来自攻略 JSON + 数值库 + 对局库，零 LLM。

### 5.1 模块①：层数进度模块

**职责**：追踪当前层数、速度、里程碑达成情况，提醒关键节点。

| 规则 | 触发 | 提醒内容 |
|---|---|---|
| 里程碑预警 | 层数进入 [10, 25, 50, 100, 200, 300, 400, 500, 625, 1000, 1250] 前 1 层 | "下一档奖励：XXX，还差 1 层" |
| 速度健康度 | 每阶段末检查 | "阶段3结束仅 180 层，低于连胜流基准 250，建议下阶段锁 2 个高层数任务" |
| 达标即停 | 层数 ≥ 500 且血量 < 40 | "已到 500 层分水岭+岩宝，超级时间挑战达标即停，别贪" |
| 任务断连风险 | 连胜/连败任务进行中，预测下回合胜负可能反转 | "连胜任务第5场，对位预测胜率 35%，断连风险高——考虑提前放弃此任务止损" |

### 5.2 模块②：战力评分模块

**职责**：给场上 8 家（含自己）打战力分，追踪趋势。

**评分公式（启发式，权重自校准）**：

```
战力分 = w1×星级分 + w2×羁绊分 + w3×成装分 + w4×血量趋势分

星级分 = Σ(弈子数 × cost权重)：三星五费=8.0, 三星四费=6.0, 三星三费=4.5, 二星四费=3.0, 二星三费=2.2 ...
羁绊分 = Σ(激活羁绊数 × 断点权重)：以绪塔尔8=6.0, 6=3.5, 4=2.0 ...
成装分 = Σ(成装数 × 装备等级权重)：神器=2.5, 光明=2.0, 成装=1.0 ...
血量趋势分 = 近5回合血量变化斜率 × k（掉血快=阵容未成型，加分警示）
```

初始权重 w1=0.35、w2=0.25、w3=0.25、w4=0.15，每 50 局用 SQLite 历史胜负数据回归重估一次，逐步收敛到稳定值。

### 5.3 模块③：对位预测模块

**职责**：预测下回合对手与胜率区间。

**输入**：回合公告 OCR（"下回合将对阵 XXX"）+ 对手最新快照 + L1.75 对位引擎输出。

**输出三档**：
- 高胜率（≥65%）：激进拿质量
- 五五开（35%-65%）：提示对手关键弈子/装备，人决策
- 低胜率（<35%）：**掉层保血策略**：提示"预测胜率 28%，建议卖血养层数，别追质量"——连败流的核心操作

**零成本增强**：备战界面常驻下家棋盘预览（游戏自带功能，工具识别后在其上标注克制提示）。

**判错分层归因（四象限统计）**：每条对位预测落库时带置信度档位，复盘时按 2×2 统计——高置信×对 / 高置信×错 / 低置信×对 / 低置信×错：

| 象限 | 含义 | 动作 |
|---|---|---|
| 高置信×对 | 引擎正常 | — |
| 高置信×错 | **引擎真烂**，规则有系统性盲区 | 复盘定位盲区，优先修 |
| 低置信×对 | 蒙对的，运气 | 不计入校准正向样本 |
| 低置信×错 | 引擎自知不确定 | 观察量，不触发升级 |

只有"高置信×错率"才是引擎真实判错率，M5 验收的 ≤15% 按此口径统计，防止蒙对样本污染回归校准。

### 5.4 模块④：影响推演模块

**职责**：把胜负的影响翻译成对四个进度条的影响，交叉提醒。

四路交叉：**胜负 → 任务（断连风险）× 层数（7以绪赢局+50碎片）× 血量（连败保血公式）× 名次（超级时间达标即停）**。

典型提醒：
- "输这局：连败任务保住+7血，但错过 +50 碎片；赢这局：碎片到手但连败断了。当前血量 62，建议故意输"（连败流场景）
- "赢这局进前4：层数差 40 到 625 档。输这局保连败：多 7 滴血。血量 35 —— 建议赢，别赌下一局"
- "血量 15 检测到超级时间挑战已达标 2/3，第三档达标即停，不追了"

## 6. 对位引擎分级与 L1.75 折中方案

### 6.1 五档全景

| 档位 | 名称 | 内容 | 工程量 | 精度 | 判定 |
|---|---|---|---|---|---|
| L0 | 查表法 | 羁绊克制表 + 星级压制，纯 lookup | 1-2 周 | ~70% | 已含在基础版 |
| L1.5 | 属性对比 | 面板数值加权对比 + 装备查表 | +2 周 | ~85% | 基础版目标 |
| **L1.75** | **混合仿真** | **主C精细 + 炮灰折算** | **6-8 周** | **~90%** | **推荐目标** |
| L2 | 全量仿真 | 60+ 弈子技能脚本全写 | 3-6 个月 | ~95% | 不做（技能脚本无底洞） |
| L2.5 | 复刻级仿真 | 对标 tacticians-academy | 社区级长线 | ~98% | 不做（无数据源） |

### 6.2 L1.75 详细设计

**核心思想**：胜负手通常由双方主 C 和关键羁绊弈子（约 15-20 个）决定，其余 40+ 弈子只影响过程不影响结论。**只给主流主C + 关键羁绊弈子写精细仿真脚本，其余按面板 DPS/坦度折算成"炮灰单元"。**

```
仿真输入：双方阵容快照（弈子×星级×装备×站位）
    ↓
数值装配：套羁绊/装备加成 → 生成结算面板
    ↓
单元分类：主C/关键羁绊弈子 → 精细单元（完整技能循环）
          其余弈子 → 炮灰单元（仅 DPS/EHP 面板值）
    ↓
tick 循环（0.1s/步）：索敌 → 平A攒蓝 → 技能结算（仅精细单元）→ 伤害折减
    ↓
Monte Carlo × 1000 次采样（重掷暴击/闪避/目标随机性）
    ↓
输出：胜率区间（如 62% ± 5%）
```

**为什么停在 L1.75 而不是 L2**：
1. 技能脚本是纯手写，60 个弈子×3 星级从实测/视频反推，8-12 周无底洞
2. 金铲铲没有官方数值基准可对答案，仿真准不准只能实战回测慢慢校
3. 每版本追更把维护成本放大到 1-2 天/版本，弃更即失效

**升级触发条件**（L1.5 → L1.75 的时机）：SQLite 攒 500+ 局（校准燃料）；L1.5 判错率实测 >15%；或开始做攻略内容需要量化胜率背书。

## 7. 局前卡组参谋

### 7.1 定位

纯局外工具，不需要截图、不进对局。回答"这局带哪三张时间卡片"。

### 7.2 架构

```
200+ 时间卡片 JSON 库（品阶/能量/生效阶段/效果）
    ↓
用户输入偏好（主C方向 / 偏连败流 / 偏平滑 / 传输门优先）
         ↓
组合推演器（离线，200³/6 ≈ 130万组合剪枝到 200-300 组）
    ↓
评分维度：强度曲线 × 任务兼容 × 传送门匹配 × 成型难度
    ↓
输出 Top 5 卡组 + 每个卡组的阶段策略说明
```

### 7.3 评分维度

| 维度 | 权重 | 说明 |
|---|---|---|
| 强度曲线 | 0.35 | 卡组在不同阶段的战力加成曲线，平于或高于同费平均 |
| 任务兼容 | 0.30 | 与 38 任务逐阶段变体表的兼容度（如「以绪塔尔任务要求 7 以绪在场，卡组需支持以绪过渡」） |
| 传送门匹配 | 0.20 | 通往强力羁绊的桥梁（如以绪→术士的传送门卡） |
| 成型难度 | 0.15 | 三卡中高费卡占比、对运营节奏的要求 |

### 7.4 与局内模块联动

局前选定的卡组作为「本局卡组预案」注入决策层：局内层数进度模块会按预案卡组的任务兼容性调整任务推荐——例如预案带「术士传送门」，则任务推荐自动偏向术士兼容任务。

## 9. 数据沉淀：SQLite 全场快照

### 9.1 库表设计

```sql
-- 对局主表
CREATE TABLE matches (
    id INTEGER PRIMARY KEY,
    start_time TEXT, end_time TEXT,
    version TEXT,           -- 游戏版本号（如 18.6）
    final_layers INTEGER,   -- 最终层数
    final_place INTEGER,    -- 最终名次
    win_loss TEXT           -- W/L 序列（如 "LLWWL..."）
);

-- 回合快照表（每回合一行）
CREATE TABLE rounds (
    id INTEGER PRIMARY KEY,
    match_id INTEGER REFERENCES matches(id),
    round_no INTEGER,
    my_units TEXT,          -- JSON: [{id, star, items}]
    my_layers INTEGER,      -- 层数
    my_hp INTEGER,          -- 血量
    my_gold INTEGER,        -- 金币
    opponent_snapshot TEXT, -- JSON: 下回合对手阵容
    predicted_winrate REAL, -- 对位引擎预测胜率
    actual_result TEXT      -- W/L/故意输
);

-- 模板确认表
CREATE TABLE templates (
    id INTEGER PRIMARY KEY,
    unit_id TEXT, star INTEGER, img_path TEXT,
    status TEXT DEFAULT 'pending',  -- pending/confirmed
    version TEXT
);
```

### 9.2 数据闭环

```
对局结束 → 快照落库 → 每50局回归重估战力评分权重
                ↓
        判错复盘：预测胜率 vs 实际胜负
                ↓
    判错率 > 15% 且持续两版本 → 触发引擎升级评估
```

### 9.3 复盘回放 CLI（M3 后叠加，+2-3 天）

```bash
tft-copilot replay --match 42        # 逐回合回放：快照 + 预测胜率 vs 实际结果
tft-copilot replay --match 42 --round 14   # 跳到指定回合
tft-copilot stats --quadrant         # 判错四象限统计
tft-copilot export --csv out/        # 一键导出 CSV
```

回放器是校准基础设施：权重回归、判错复盘、截图标注都依赖它。不做回放器，后面每个数字的校准成本都会翻倍。

### 9.4 导出与分析

- 一键导出 CSV（Polars 处理）供 Power BI 可视化——无缝衔接 Excel/CSV/SQL→Polars→DuckDB→PowerBI 分析工具链
- 预设看板：层数达成分布、任务选择与名次相关性、连败流vs连胜流胜率对比

### 9.5 断线续采（状态机持久化）

工具崩溃或误关后重开，从 SQLite 恢复当前对局上下文（回合号、层数基线、锁定任务），当前局数据不丢：
- 场景状态机每回合落库一次（rounds 表已有，零新增表）
- 启动时检测"未闭合对局"（matches 表 end_time IS NULL）→ 提示"继续上局"或"开新局"
- 工程量 +1 天，与感知调度器同步实现

## 10. 安全与合规红线

### 10.1 三条红线（铁律）

| # | 红线 | 检测面 |
|---|---|---|
| 1 | **零输入模拟** | 不模拟鼠标键盘。ACE 检测的是统计学行为特征（固定间隔/无抖动轨迹/超人类反应/像素级精度），工具完全无输入 = 零暴露 |
| 2 | **零进程读取** | 不读内存/句柄/网络包。ACE TP 驱动层直接检测进程句柄与内存读取，碰即死 |
| 3 | **零联网外传** | 数据不出本机。上传云端校准/云胜率库 = 增加暴露面 + 违反个人工具定位 |

### 10.2 为什么"截屏只读"几乎无风险

1. **ACE 三层检测对截屏全盲**：TP 驱动层管内存/句柄，服务器回放层管输入行为，AI行为层管操作规律——工具不产生输入、不读内存、不联网，三层都无感知对象
2. **截屏 API 是合法系统调用**：mss 走 GDI/DXGI 系统接口，与 OBS 录屏同源，不属于逆向
3. **行为侧人机分工清晰**：所有需要"导航"的操作（按Tab轮播、按E列表、拖棋子）由人完成，工具是"看着你操作的记录员"

### 10.3 灰色地带决策记录

| 决策点 | 决策 | 理由 |
|---|---|---|---|
| 解包客户端拿数值 | **不做** | 腾讯加壳 + 用户协议禁逆向 + 与只读定位冲突 |
| 自动翻页看7家对手 | **不做** | 输入模拟触红线1；改用官方 Tab 轮播 + 人工导航 |
| 云端胜率库 | **不做** | 触红线3；本地 SQLite 自校准够用 |
| 爬掌盟 H5 | **做，半自动** | 公开页面 + 限频 + robots.txt 合规 |
| LLM 进运行时 | **不做** | 延迟/成本/可解释性三输，规则引擎足够 |
| OCR 用云端 API | **不做** | 触红线3；PaddleOCR 本地推理够用 |
